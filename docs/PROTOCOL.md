# 와이어 프로토콜

클라이언트와 서버가 주고받는 바이너리 패킷 형식의 규격. 리액터의 수신 경로와 Session 버퍼링이 이 문서의 규칙을 따른다.

프로젝트 개요와 아키텍처는 [README](../README.md)를, 이 규격을 처리하는 코드의 설계는 [설계](DESIGN.md#프로토콜-처리)를 참고.

## 프레임 구조

모든 패킷은 4바이트 헤더로 시작한다.

```
 byte   0        1        2        3
      +--------+--------+--------+--------+
    0 |   payload_len   |      type       |
      +--------+--------+--------+--------+
    4 |  payload (payload_len bytes)      |
      |                ...                |
      +-----------------------------------+
```

| 필드 | 크기 | 설명 |
|---|---|---|
| `payload_len` | u16 | **페이로드만의 길이. 헤더 4바이트는 포함하지 않는다.** |
| `type` | u16 | 메시지 종류 |

**`payload_len`이 헤더를 포함하지 않는다는 점을 특히 주의한다.** 이 규약이 양쪽에서 어긋나는 것이 길이-프리픽스 프로토콜의 대표적 버그다.

### 왜 u16인가

길이 필드를 u16으로 두면 **한 패킷이 구조적으로 65535바이트를 넘을 수 없다.** 악의적인 클라이언트가 거대한 길이를 보내 서버에 대량 할당을 유발하는 공격이 형식 차원에서 차단된다. u32를 쓰면 어차피 코드에서 상한을 검사해야 하는데, 그 검사를 형식이 대신하는 셈이다.

대신 64 KiB를 넘는 응답은 애플리케이션 수준에서 페이지네이션해야 한다(예: 채팅 히스토리 조회). 이는 어차피 필요한 설계다.

### 바이트 순서

**모든 다중 바이트 정수는 빅엔디언(네트워크 바이트 순서).**

x86끼리 통신하므로 리틀엔디언이 변환 비용이 없다는 주장이 가능하지만, 패킷당 몇 바이트에 대한 `bswap` 비용은 무시할 수준이고, 표준 관례를 따르는 편이 패킷 덤프를 표준 도구로 읽을 때 유리하다.

## 필드 인코딩

페이로드 안의 필드는 아래 원시 타입의 나열이다. 구분자나 패딩은 없다.

| 타입 | 인코딩 |
|---|---|
| `u8` `u16` `u32` `u64` | 빅엔디언 부호 없는 정수 |
| `i64` | 빅엔디언, 2의 보수 |
| `string` | `u16` 바이트 길이 + UTF-8 바이트열. **널 종료 문자 없음** |

`string`의 길이는 문자 수가 아니라 **바이트 수**다. UTF-8에서 한글 한 글자는 3바이트다.

## 메시지 타입

방향에 따라 번호 대역을 나눈다. 서버는 클라이언트가 보낸 `0x8000` 이상의 타입을 **즉시 거절**한다. 클라이언트가 서버 전용 메시지를 위조해 보내는 경우를 대역 검사만으로 걸러낼 수 있다.

| 대역 | 방향 |
|---|---|
| `0x0001` ~ `0x7FFF` | 클라이언트 → 서버 |
| `0x8000` ~ `0xFFFF` | 서버 → 클라이언트 |

### 메시지 목록

| 타입 | 이름 | 방향 |
|---|---|---|
| `0x0001` | `LOGIN_REQ` | C→S |
| `0x0002` | `JOIN_ROOM_REQ` | C→S |
| `0x0003` | `LEAVE_ROOM_REQ` | C→S |
| `0x0004` | `CHAT_REQ` | C→S |
| `0x0005` | `PING_REQ` | C→S |
| `0x8001` | `LOGIN_RES` | S→C |
| `0x8002` | `JOIN_ROOM_RES` | S→C |
| `0x8003` | `LEAVE_ROOM_RES` | S→C |
| `0x8004` | `CHAT_NTF` | S→C |
| `0x8005` | `USER_JOINED_NTF` | S→C |
| `0x8006` | `USER_LEFT_NTF` | S→C |
| `0x8007` | `PONG_NTF` | S→C |
| `0x80FF` | `ERROR_NTF` | S→C |

틱 기반 상태 동기화로 확장하면 스냅샷 타입이 추가되지만 **프레임 형식은 바뀌지 않는다.** 대역에 번호를 더할 뿐이다.

## 페이로드 정의

### C→S

```
LOGIN_REQ (0x0001)
    u16     protocol_version
    string  username
    string  password

JOIN_ROOM_REQ (0x0002)
    u32     room_id

LEAVE_ROOM_REQ (0x0003)
    (페이로드 없음, payload_len = 0)

CHAT_REQ (0x0004)
    string  text

PING_REQ (0x0005)
    (페이로드 없음, payload_len = 0)
```

### S→C

```
LOGIN_RES (0x8001)
    u8      result          -- 결과 코드, 0 = 성공
    u64     user_id         -- 실패 시 0

JOIN_ROOM_RES (0x8002)
    u8      result
    u32     room_id
    u16     member_count    -- 본인 포함, 입장 후 인원

LEAVE_ROOM_RES (0x8003)
    u8      result

CHAT_NTF (0x8004)
    u64     user_id
    string  username
    string  text
    i64     sent_at_ms      -- Unix epoch 밀리초

USER_JOINED_NTF (0x8005)
    u64     user_id
    string  username

USER_LEFT_NTF (0x8006)
    u64     user_id

PONG_NTF (0x8007)
    (페이로드 없음, payload_len = 0)

ERROR_NTF (0x80FF)
    u16     code
    string  message         -- 사람이 읽기 위한 것. 클라이언트 분기는 code로 한다
```

## 결과 및 에러 코드

`result` (u8): 각 `*_RES`에 사용

| 값 | 의미 |
|---|---|
| `0` | 성공 |
| `1` | 인증 실패 (잘못된 자격 증명) |
| `2` | 대상 없음 (존재하지 않는 룸) |
| `3` | 상태 위반 (로그인 전 요청, 이미 입장한 상태에서 재입장 등) |
| `4` | 정원 초과 |

`code` (u16): `ERROR_NTF`에 사용

| 값 | 의미 | 이후 처리 |
|---|---|---|
| `1000` | 잘못된 프레임 (길이/타입 위반) | 연결 종료 |
| `1001` | 알 수 없는 메시지 타입 | 연결 종료 |
| `1002` | 방향 위반 (클라이언트가 S→C 타입 전송) | 연결 종료 |
| `1003` | 필드 검증 실패 (길이 초과 등) | 연결 유지 |
| `1004` | 프로토콜 버전 불일치 | 연결 종료 |
| `1005` | 송신 버퍼 초과 (백프레셔) | 연결 종료 |
| `1006` | 서버가 연결을 받지 않음 (정원 초과, 로그인 기한 초과) | 연결 종료 |

`1006`은 **피어가 뭔가 잘못해서 나가는 코드가 아니다.** 나머지가 전부 "상대가 규약을 어겼다"인 것과 달리, 이건 서버 쪽 사정(더 받을 자리가 없거나, 붙어놓고 로그인을 하지 않았거나)이다. 두 사유에 코드를 하나만 준 이유는 클라이언트가 어느 쪽이든 같은 판단(물러났다가 나중에 다시)을 하기 때문이고, 어느 쪽이었는지는 `message`가 사람에게 알려준다. 자세한 정책은 [연결 정원과 로그인 기한](#연결-정원과-로그인-기한)에 있다.

`1005`는 **서버가 실제로 전송하지 않는다.** 이 한도에 도달했다는 것 자체가 상대가 소켓을 비우지 않고 있다는 뜻이라, 통지를 보내봐야 이미 너무 길어진 큐에 한 줄 더 얹을 뿐이다. 서버는 말없이 끊는다. 번호는 다른 용도로 재사용하지 않도록 카탈로그에 남겨둔다.

`CHAT_REQ`는 대응하는 `*_RES`가 없어서, 로그인 전이거나 룸 밖에서 보낸 경우처럼 상태 위반을 알릴 곳이 `ERROR_NTF`뿐이다. 이 표에는 상태 위반에 해당하는 코드가 없으므로 서버는 `1003`을 쓴다. 연결을 살려두는 유일한 항목이고, 여기서는 그 성질이 중요하다.

`LOGIN_REQ`도 서버가 로그인을 확인할 수 없을 때(DB 장애, 로그인 과부하)는 `LOGIN_RES` 대신 `ERROR_NTF(1003)`으로 답한다. 인증 실패(`1`)로 답하면 사용자가 멀쩡한 비밀번호를 의심하게 된다. 연결은 유지되므로 클라이언트는 잠시 뒤 같은 연결에서 다시 로그인하면 된다. 로그인 기한은 그동안에도 흐른다.

## 제한값

| 항목 | 상한 | 근거 |
|---|---|---|
| `payload_len` | 65535 | u16 구조적 제한 |
| `username` | 32바이트 | DB 컬럼과 일치시킨다 |
| `password` | 128바이트 | |
| `text` (채팅) | 1024바이트 | UTF-8 기준. 한글 약 341자 |

상한 위반은 `ERROR_NTF(1003)`으로 응답하되 연결은 유지한다. 프레임 자체가 깨진 경우(`1000`~`1002`)와 구분한다. 전자는 클라이언트의 입력 실수이고, 후자는 프로토콜을 지키지 않는 상대이므로 신뢰할 수 없다.

## 유휴 타임아웃과 하트비트

서버는 **5분 동안 한 바이트도 받지 못한 연결을 끊는다.** 상대가 살아있다는 증거는 상대가 보낸 것뿐이고, 조용히 죽은 연결을 TCP가 알려주기까지는 한참 걸린다.

받기만 하고 보낼 것이 없는 클라이언트(채팅방을 눈으로만 보고 있는 경우)는 여기 걸리지 않도록 **유휴 상태에서 2분마다 `PING_REQ`를 보낸다.** 서버는 `PONG_NTF`로 답한다.

- 타임아웃 창(5분)이 핑 주기(2분)의 두 배를 넘으므로, 연속으로 두 번 넘게 놓쳐야 끊긴다
- 다른 메시지를 보냈다면 그것도 활동으로 친다. 핑은 보낼 것이 없을 때만 필요하다
- `PONG_NTF`는 클라이언트 쪽 판단용이다. 서버가 소켓만 열어둔 채 멈춘 것이 아닌지 확인한다. 서버의 타임아웃은 `PING_REQ`가 도착한 것만으로 갱신되므로 응답 자체는 서버에 필요 없다
- 로그인 전에도 보낼 수 있다. 유휴 타임아웃은 인증 여부와 무관하게 모든 연결에 적용된다
- 다만 **핑으로 로그인을 미룰 수는 없다.** 유휴 타임아웃과 로그인 기한은 다른 질문이다. 아래 참고

## 연결 정원과 로그인 기한

서버가 자기 사정으로 연결을 거절하는 두 경우다. 둘 다 `ERROR_NTF(1006)`을 보낸 뒤 끊는다.

**정원 초과.** 동시에 쥘 연결 수에 상한이 있다(`RRS_MAX_CONNECTIONS`, 기본 4096). 넘어서 들어온 연결은 세션을 만들지 않고 그 자리에서 `1006`("the server is full")을 쓰고 닫는다. 상한이 없으면 EMFILE로 발견하게 되는데, 그때 리액터가 할 수 있는 일은 accept를 멈췄다 다시 켜기를 반복하는 것뿐이라 이미 붙어 있는 연결까지 같이 느려진다. 정원은 그 지점보다 앞에서 만나라고 있는 것이고, **이미 들어와 있는 연결은 새 연결이 거절되는 것에 영향받지 않는다.**

**로그인 기한.** 연결 후 30초 안에 로그인하지 않으면 `1006`("no login before the deadline")으로 끊는다. 유휴 타임아웃(5분)과 별개인 이유는 묻는 것이 다르기 때문이다. 유휴 타임아웃은 *뭔가 하던* 연결이 조용해진 경우고, 이쪽은 *시작조차 하지 않은* 연결이다. 인증하지 않은 피어가 핑만 보내며 자리를 무한정 차지하는 것을 막는다.

기한이 다 됐는데 그 클라이언트의 로그인 응답이 아직 서버 안에 있다면(워커가 밀려 있는 경우) 끊지 않고 한 주기를 더 준다. 서버가 만든 대기를 이유로 상대를 끊는 것은 앞뒤가 맞지 않는다. 연장은 **연결당 한 번**이다. 서버는 한 주기 안에 답하지 못할 로그인을 애초에 받지 않으므로 한 번이면 충분하고, 횟수에 제한이 없으면 틀린 비밀번호를 쉬지 않고 다시 보내는 피어가 로그인을 늘 처리 중인 상태로 두어 기한을 영영 피한다.

## 파싱 규칙

수신 버퍼에서 프레임을 꺼내는 절차. 리액터가 `recv()`로 읽어 넣은 바이트를 Session이 아래대로 소비한다.

1. 버퍼에 4바이트 미만이면 **더 기다린다.** 헤더조차 잘려서 도착할 수 있다
2. `payload_len`과 `type`을 읽는다 (아직 버퍼에서 제거하지 않는다)
3. 버퍼에 `4 + payload_len` 바이트가 모이지 않았으면 **더 기다린다**
4. 한 프레임을 소비하고 디스패치한다
5. **1번으로 돌아간다.** 한 번의 `recv()`로 여러 프레임이 도착할 수 있다

### 반드시 지킬 것

- **한 번의 `recv()`가 한 개의 메시지에 대응한다고 가정하지 않는다.** TCP는 메시지 경계를 보장하지 않는다. 프레임이 잘려 오거나 여러 개가 뭉쳐 온다
- **타입 대역을 먼저 검사한다.** 페이로드를 파싱하기 전에 방향과 알려진 타입인지 확인한다
- **필드를 읽기 전에 남은 바이트 수를 확인한다.** `payload_len`이 맞더라도 그 안의 `string` 길이 필드가 페이로드 경계를 넘도록 조작될 수 있다. 각 필드 읽기는 경계 검사를 동반해야 한다

마지막 항목이 이 프로토콜에서 가장 실수하기 쉬운 지점이다. `payload_len` 검증을 통과했다고 해서 페이로드 내부가 안전한 것은 아니다.

## 의도적으로 넣지 않은 것

| 항목 | 이유 |
|---|---|
| 압축 | 메시지 대부분이 수십~수백 바이트다. 압축 헤더가 본문보다 커진다 |
| 가변 길이 정수(varint) | 고정폭이 파싱 코드가 단순하고, 이 규모에서 절약되는 바이트는 무의미하다 |
| 버전 협상 | `LOGIN_REQ`에 버전을 싣되 협상은 하지 않는다. 불일치하면 `ERROR_NTF(1004)` 후 종료. 클라이언트와 서버가 함께 배포되므로 협상이 필요 없다 |
| 시퀀스 번호 / ACK | TCP가 순서와 재전송을 보장한다. 응용 계층에서 중복 구현할 이유가 없다 |

## 알려진 한계: 자격 증명이 평문으로 전송된다

TLS를 쓰지 않으므로 `LOGIN_REQ`의 비밀번호가 네트워크에 평문으로 흐른다. 이 프로젝트의 범위에서는 다음을 전제로 수용한다.

- 실행 환경이 `docker-compose`로 띄운 로컬 네트워크다
- 목적이 비동기 I/O 구조의 검증이지 인증 체계 구축이 아니다

DB에는 평문을 저장하지 않는다. 서버가 수신 즉시 Argon2id로 해시해 비교한다. 전송 구간 보호가 필요해지면 서버 코드를 바꾸는 대신 **nginx를 앞단에 두어 TLS를 종단**하도록 한다.
